# 알림·실시간 통신 검토 (2026-10-19)

## Context
헤더 오른쪽 위 종 아이콘(`frontend/src/components/layout/Header.tsx`)은 모양만 있어요.
- 빨간 점이 항상 켜져 있고(`Header.tsx:44`), 눌러도 동작이 없어요.
- 여기에 넣을 기능과, 실시간 통신(SSE·WebSocket)을 써볼 만한 기능을 정리해요.
- 아직 구현 방식은 정하지 않았어요. 아래 "결정할 것"을 정한 뒤 계획을 세워요.

## 알림과 "처리할 일"의 구분
대시보드에는 이미 "처리할 일" 패널(발송 대기, 환불 요청, 재고 부족, 문의)과 사이드바 배지가 있어요.
알림이 같은 숫자를 또 보여주면 겹쳐요.

| | 처리할 일 | 알림 |
|---|---|---|
| 성격 | 지금 **쌓여 있는** 일 (상태) | 방금 **일어난** 변화 (사건) |
| 표시 | 건수 | 한 문장 + 시간 + 읽음 여부 |
| 예 | 환불 요청 2건 | 환불 요청이 새로 접수됐어요 · 3분 전 |

알림을 누르면 관련 화면(처리할 일, 주문 상세 등)으로 이동해요.

## 알림 후보
1. **주문·결제** (가장 기본)
   - 고액 주문이 들어왔어요 (예: 100만원 이상)
   - 환불 요청이 새로 접수됐어요 → 처리할 일의 "환불 요청"으로 이동
   - 결제 실패가 최근 1시간에 평소보다 많아요
2. **재고·상품**
   - ○○ 상품이 품절됐어요
   - ○○ 상품 재고가 10개 아래로 떨어졌어요
3. **고객**
   - 1:1 문의가 새로 들어왔어요
   - 별점 1~2점 리뷰가 등록됐어요
4. **이상 감지** (대시보드 데이터 활용)
   - 지난주 같은 시간보다 주문이 30% 줄었어요
   - 방문자가 갑자기 많아졌어요
   - 하단 KPI의 전일·지난주 비교값(`Kpi.comparisons`)이 기준을 넘으면 알림을 만드는 방식
5. **작업 완료**
   - 엑셀 다운로드가 준비됐어요
   - 쿠폰 일괄 발송이 끝났어요 / 실패했어요
   - 이번 달 정산 리포트가 만들어졌어요
6. **보안·계정**
   - 새 기기에서 로그인했어요
   - 관리자 권한이 변경됐어요

### 처음 만든다면 (MVP)
- 종을 누르면 드롭다운 목록. 각 항목은 아이콘, 해요체 한 문장, 상대 시간("3분 전"), 안 읽음 표시.
- 빨간 점은 **안 읽은 알림이 있을 때만** 켜요. "모두 읽음" 버튼.
- 내용은 1(주문·결제)과 2(재고)부터. 처리할 일 패널과 연결되고 mock으로 만들기 쉬워요.
- API (기존 응답 규격 `{statusCode, code, data}` 그대로)
  - `GET /api/v1/notifications`: 목록
  - `PATCH /api/v1/notifications/{id}/read`, `PATCH /api/v1/notifications/read-all`: 읽음 처리
- 파일 배치는 기존 규칙대로 `schemas/notification.py`, `crud/notification.py`, `api/v1/routes/notifications.py`.

## 실시간 통신 방식
| 방식 | 방향 | 맞는 용도 | FastAPI |
|---|---|---|---|
| 폴링 (몇 초마다 다시 요청) | 브라우저 → 서버 | 아주 단순한 갱신 | 기존 API 그대로 |
| **SSE** (Server-Sent Events) | 서버 → 브라우저 **한 방향** | 알림, 실시간 숫자, 주문 피드 | `fastapi.sse.EventSourceResponse` (공식 스킬 권장) |
| **WebSocket** | **양방향** | 채팅, 접속자 표시, 함께 편집 | `@router.websocket` 기본 내장 |

- 알림처럼 서버가 알려주기만 하면 되는 기능은 **SSE로 충분**해요. 끊기면 브라우저(`EventSource`)가 자동으로 재연결해요.
- **WebSocket**은 브라우저도 계속 서버에 보내야 하는 기능에서 필요해요.
- Laravel로 치면 Reverb/Echo 브로드캐스팅에 해당해요.

## 실시간으로 만들어 볼 만한 기능
1. **실시간 주문 피드** (데모로 가장 좋음)
   - 새 주문이 들어오면 "오늘 들어온 주문" 표 맨 위에 행이 바로 추가되고, 종에 알림이 떠요.
   - 백엔드가 몇 초마다 가짜 주문을 만들어 보내면 DB 없이 확인할 수 있어요.
   - SSE로도 되지만, 소켓 연결·끊김·재연결을 익히기 좋은 주제예요.
2. **관리자 접속·작업 중 표시** (WebSocket이 꼭 필요)
   - "김OO님이 이 주문을 보고 있어요", "이OO님이 환불 처리 중이에요"
   - 두 관리자가 같은 주문을 동시에 처리하는 사고를 막아요.
   - 브라우저가 "지금 이 화면을 보고 있다"를 계속 보내야 해서 양방향이 필요해요.
3. **1:1 문의 실시간 채팅** (WebSocket 대표 예)
   - 고객용 화면도 필요해서 지금 범위보다 커요.
4. **오늘 매출 실시간 증가**
   - 위쪽 "오늘 ○○만원"이 주문이 들어올 때마다 올라가요. 1번과 묶으면 자연스러워요.

## 구조상 알아둘 점
- **브라우저가 FastAPI에 직접 연결해야 해요.**
  지금 대시보드 데이터는 Next 서버가 백엔드를 불러 화면을 만들어요(`frontend/src/lib/api.ts`, 서버 전용 `API_URL`).
  실시간 연결은 클라이언트 컴포넌트에서 열어야 해서 브라우저용 주소(`NEXT_PUBLIC_API_URL`)가 따로 필요해요.
- **CORS·Origin**: 백엔드 CORS는 `FRONTEND_HOST`(`http://localhost:3001`)만 허용해 둬서 SSE는 그대로 돼요.
  WebSocket은 CORS 대상이 아니라서 연결할 때 `Origin` 헤더를 직접 확인해야 해요.
- **여러 프로세스로 늘릴 때**: 연결이 프로세스마다 따로 잡혀서 Redis pub/sub 같은 중계가 필요해요.
  개발 단계(`fastapi dev`, 프로세스 하나)에서는 신경 쓰지 않아도 돼요.
- **인증**: 지금은 로그인이 없어서 생략할 수 있어요. 로그인을 붙이면 SSE·WebSocket 연결에도 인증을 넣어야 해요.
- **응답 규격**: SSE·WebSocket 메시지는 HTTP 응답이 아니라서 `{statusCode, code, data}` 틀을 그대로 쓰지 않아요.
  메시지 형식(예: `{ "type": "order.created", "data": {...} }`)을 따로 정해요.
